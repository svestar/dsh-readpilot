# 功能规划

已实现能力见[功能索引](features/index.md)。本页只记候选方向，不构成交付承诺；落地时按 `docs/templates/feature.md` 新建 FTR，并同步测试与索引。

## 0.2+

能力层面继续加功能收益低：解释、追问、总结、批判这类需求，几条提示词就能覆盖，为它们造引擎是过度工程。插件不可替代的是上下文装配与结果落地——把选段、书名、章节、笔记和进度自动填进提示词，并把回答写回原文位置。判断标准：这条需求能否只用提示词实现？能，就进提示词库；不能，才写代码。

- **提示词预设** —— 内置解释这段、术语、翻译、追问作者、批判论点、总结本章；变量 `{{selection}}`、`{{book}}`、`{{chapter}}`、`{{notes}}`；入口为选段工具条与输入框 `/`；模板存书库目录，可增删改。
- **基础体验补全** —— 真实封面（复用 `assets/` 与 `cache/pages/` 缓存）、阅读状态与评分（`library-meta.json` 扩为 `status` 与 `rating`）、键盘快捷键（翻页、搜索、书签、Esc）、批注总览（按章节与颜色筛选、点击跳回原文）、回答存为批注。

## 0.3：让 agent 操控插件

提示词只能改变它说什么，工具才能改变它做什么。现状的工具几乎全是只读，写操作只落数据、不驱动界面；通道也只有客户端调 Host，Host 无法主动推送。0.3 补的是动作能力，不是更多查询。

- **感知** —— 当前书、章节、可见范围、选中文字。现在只注入书名与章节，选区和视口未知；没有感知的动作就是瞎指挥。
- **动作** —— 少而正交：`reader_goto`（章节 / 页码 / 字符位置）、`reader_mark`（划线、批注、书签）、`reader_open_panel`、`reader_tag`、`reader_status`。
- **可撤销** —— 每个动作有回执、界面留痕、可一键撤销；不可撤销的动作不给 agent。默认是提议而非执行，避免抢方向盘。
- **原则** —— agent 与用户走同一条代码路径、同一套校验、同一个撤销栈，不开后门写接口；写笔记仍走草稿确认。
- **分期** —— 先用深链动作验证：agent 输出可点动作，用户点击后执行，复用现有跳转拦截，零架构改动。验证有需求后再上命令队列与反向通道，并单独立 ADR。
